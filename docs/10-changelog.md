## 1. 版本策略（先读这一段）

| 规则 | 说明 |
| --- | --- |
| 路径内带版本 | 接口路径里的 `v1` 是**主版本**；主版本内**只增不改** |
| 字段只增 | 主版本内**不删除、不改名、不改语义**；新字段一律可选 |
| 不兼容变更 | 必须升 `v2` 并**与 `v1` 平行运行至少一个公告周期**（先公告、后下线） |
| 公告先行 | 任何影响商家代码的变更，先发公告，再改行为 |
| 同源发布 | 每次发版在三处同源发布：**门户公告栏**（平台内的商家公告位）、**本文档「更新日志」**、**公开发布页**；公告正文只有一份（见 `releases/`） |

**你要做的**：对 `code` 与字段做**宽松解析**（多字段不报错），对新增枚举值做兼容分支；这样主版本内的变更不会打断你。

## 3. 更新日志

### v1.0.0

**新增**

- **支付宝官方收款码面向商家下发**：下单响应新增 `qrCode` 字段（仅支付宝渠道、服务端校验官方前缀后下发），商家可在**自有 PC 页面**直接渲染官方收款码，与平台收银页同形。
  - 下发语义：**只有下发响应有效**；查询接口恒为 `null`；需要新码走**重拉起**端点（新尝试=新码）。
  - 覆盖三个端点：创建订单（下发）、重拉起（换新码）、查询（恒空）。
- **收银页终端分端能力**：同一收银 URL 按终端分派——PC 渲染二维码；手机浏览器（微信外）支付宝单给**手势主按钮「打开支付宝」**（渲染顺序=二维码 → 主按钮 → 按钮下的兜底说明，三样都在买家手势之前已渲染；**无手势的自动跳转已被真机证伪，不再采用**）；手机微信内支付宝单不自动跳转（只给复制链接引导）。
- **微信支付「免手点」**：手机微信内进入收银页即自动完成授权并调起支付面板，买家无需先点一次按钮。
- **手机微信外推荐路径**：微信支付单在手机微信外给出**可执行**的一键引导（复制链接并打开微信 + 三步说明 + 如实兜底），逐字文案见 [收银页对接 · 第 4 节](./06-cashier-integration.md#4-手机微信外推荐路径逐字引导文案)。

**明确不支持（不要按这些形态设计）**

- 微信**没有**「正扫」形态：微信的 PC 扫码本质是**中转链**（二维码 → 手机微信内 → 页面调起）。
- 手机浏览器（微信外）**没有**「直接拉起微信支付」形态。
- 商家的自有 App **不得**用 WebView 内嵌打开收银页（必须跳系统浏览器）。

**迁移动作**：无需迁移。本次为**只增不改**：新字段 `qrCode` 为可选，旧解析逻辑不受影响；收银页行为变化只作用于买家侧体验，商家的服务端对接无需改动。

#### 变更（2026-09-27）：不再要求 SVIP 资格

开放平台**整条线**不再以会员等级（SVIP）为判据（产品负责人决定）：

- 应用一键申请的自动审核**不再因非 SVIP 转人工**（判据版本 `openapi-auto-review-v2`）；
- 商家 API 的**新增下单与重拉起不再要求 SVIP**——原来的「SVIP 资格」`403` 拒绝码**已从错误码总表移除**（若你的代码里有它的分支，可以删掉；保留也不会再被触发）；
- 已有的历史申请记录不受影响（历史判据结果原样保留）；商家准入仍要求**商家状态 ACTIVE** 且未被风控冻结。

**迁移动作**：无需迁移。若你的接入文档/代码里写着"需要 SVIP"，请一并删除该前置描述。

#### 文档修订（2026-09-27）

本轮为**对齐线上实际行为**的资料修订（无接口行为变更，接口侧唯一一处见下），要点：

- **关单 / 重拉起**：明确这两个端点**无请求体字段，但仍必须带 `Content-Type: application/json`**（接口侧同步修正为「空请求体按无请求体处理」——修复前不带请求体会被 `400` 拒，属缺陷修复，对已按文档接入的商家只会变宽松）。
- **请求头**：补齐六头的长度与字符集约束（`nonce` 16–64 位、`requestId` 8–128 位等）；越界与缺失共用同一句 `400`。
- **响应验签**：补齐 `CONTENT_TYPE` 归一化规则（小写、去 `;` 参数），并写明**哪些响应不带** `X-XD-Response-*`（鉴权链之前的拒绝）——按旧文做强制验签会每个响应都失败。
- **`X-XD-Request-Id` 例外**由两类更正为三类（增加请求体门卫拒绝）。
- **`notifyUrl`**：补齐四项真实前置（绝对 HTTPS、host 必须属于已验证域名、短信二次验证、审核通过才生效），并写明**未配置/未通过 = 不产生事件、事后不可补发**。
- **乱序判据**：`stateVersion` 当前恒为 `0`，改为按状态机判新旧。
- **回跳语义**：`returnUrl` 不是自动跳转，需买家点「返回商家」，且仅同一页面会话提供。
- **通道口径**：通道放行由平台整体控制、无自助查询面（原「去门户确认你的应用放行情况」有误）。
- **限额口径**：限额不在门户展示，调整走反馈渠道（原指引入口不存在）。
- **域名验证**：绝大多数失败是**终态**，需重新签发（原「核对后重新验证」会撞 `409`）；补单次申报上限 10 个。
- **指纹自检**：明确 PEM 的规范化规则（统一换行、去首尾空白后再取 SHA-256）。
- **示例与 demo**：示例补 `replayed`/`thresholdFen`、重试条目补「nonce 必须换新」、修正 PHP 覆盖声明与自检命令的工作目录；demo 修正 PC 微信单文案、去掉真实收银页没有的复制入口，并如实标注「通道闸门与四道前置门未模拟」。
- **接入地址（Base URL）下发面**：此前资料只说「开通时提供」、又不许印 host，卖家无处可取；现在**登录门户「应用凭证」页**即可看到并复制「接入地址」，文档同步改写（见 [接入指南 §1](./02-integration-guide.md)）。

#### 文档修订（2026-09-27 · 全量对齐复核批）

本轮为 12 篇文档 + Skill + 示例 + demo 与服务端实现的**逐条对齐复核**后的资料修订（无接口行为变更），修掉的是上一轮修订的漏网残留与表述例外：

- **通道口径残留清理**：简介/FAQ 里「微信要看你这个应用放行了没有」「先在后台确认你的应用放了哪几条通道」为旧口径残留——通道放行由**平台整体控制、不区分应用**，后台没有查询面，以平台公告/对接人通知为准（与 [收银页对接 §1](./06-cashier-integration.md) 的修订同源）。
- **限额口径残留清理**：错误码表与 Skill 里「生效限额以门户展示为准」为旧口径残留——限额**不在任何页面展示**，被拒后先关在途订单、需调整走反馈渠道（与 [费率与限额](./07-fees-and-limits.md) 的修订同源）。
- **反馈渠道落点更正**：全部「门户反馈渠道」更正为「**官网反馈渠道**」（门户内暂无反馈提交入口，平台反馈统一走官网反馈链；门户结算页既有指引同此口径）。
- **失败信封例外**：写明来源 IP 拒绝（`403`）的信封另带一个 `details` 字段，内容只有 `reason` 或你的 `appId`，不回显平台观测到的地址。
- **六头重复例外**：同名头重复的 `400` 会在 message 里点名该头（缺失/形态越界仍不点名；每个头只提交一次即可避开）。
- **回源文件验证判据**：写明实际判据是「页面内容包含验证码」；「原样只返回验证码」是最稳妥做法而非硬性要求。
- **事件丢失路径补全**：平台侧内部异常同样可能导致事件未产生——查单补偿路径必须接（与 [上线检查清单 D6](./11-go-live-checklist.md) 互为呼应）。
- **demo 能力如实化**：demo README 补「通道闸门与前置门未模拟」标注（与本日志上一批的表述对齐）；快速开始的能力清单以 demo 冒烟实际覆盖为准（不含轮询步骤）。
- **查询退款的 `replayed`**：写明查询返回中该字段恒为 `true`（既有记录投影），勿当作幂等重放信号。
- **Skill 修订**：`APP_REVOKED` 行补「实际拿到的是 `401`」防枚举口径；`SKILL.md` 铁律 7 的限额口径同步。

## 4. 已取消/不支持的形态（历史公告残留，防误用）

平台**不提供**下列形态，任何历史资料、截图或口口相传里的这些说法都不成立：

- 微信「原生扫码」直出付款码（见上：不存在）。
- 手机浏览器直接拉起微信支付面板。
- 平台侧托管收款页（收款页形态只有本资料描述的两类：自渲染官方收款码 / 平台收银页）。
- 在本资料里出现过的任何「时效承诺」或「固定费率」——均已作废，一律以**生效配置**与**每单投影**为准。
