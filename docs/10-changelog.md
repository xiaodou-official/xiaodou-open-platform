## 3. 更新日志

### v1.0.0

**新增**

- **支付宝官方收款码面向商家下发**：下单响应新增 `qrCode` 字段（仅支付宝渠道、服务端校验官方前缀后下发），商家可在**自有 PC 页面**直接渲染官方收款码，与平台收银页同形。
  - 下发语义：**只有下发响应有效**；查询接口恒为 `null`；需要新码走**重拉起**端点（新尝试=新码）。
  - 覆盖三个端点：创建订单（下发）、重拉起（换新码）、查询（恒空）。
- **收银页终端分端能力**：同一收银 URL 按终端分派——PC 渲染二维码；手机浏览器（微信外）支付宝单给**手势主按钮「打开支付宝」**（渲染顺序=二维码 → 主按钮 → 按钮下的兜底说明，三样都在买家手势之前已渲染；**无手势的自动跳转已被真机证伪，不再采用**）；手机微信内支付宝单不自动跳转（只给复制链接引导）。
- **微信支付「免手点」**：手机微信内进入收银页即自动完成授权并调起支付面板，买家无需先点一次按钮。
- **手机微信外推荐路径**：微信支付单在手机微信外给出**可执行**的一键引导（复制链接并打开微信 + 三步说明 + 如实兜底），逐字文案见 [收银页对接 · 第 4 节](./06-cashier-integration.md#4-手机微信外推荐路径逐字引导文案)。

**明确不支持（不要按这些形态设计）**

- 微信**没有**「正扫」形态：微信的 PC 扫码本质是**中转链**（二维码 → 手机微信内 → 页面调起）。
- 手机浏览器（微信外）**没有**「直接拉起微信支付」形态。
- 商家的自有 App **不得**用 WebView 内嵌打开收银页（必须跳系统浏览器）。

**迁移动作**：无需迁移。本次为**只增不改**：新字段 `qrCode` 为可选，旧解析逻辑不受影响；收银页行为变化只作用于买家侧体验，商家的服务端对接无需改动。

#### 变更（2026-09-28）：来源 IP 校验可自助开启/关闭

原来只能由平台侧调整的「来源 IP 校验」开关，现在**由你自己在门户掌握**（产品负责人决定）：

- 门户「IP 白名单」页新增**自助开关**：关闭/开启都需**短信二次验证**，平台全程留痕；
- **关闭不动清单**：白名单条目原样保留（不会因为关掉校验而丢），重新开启是一键的事；
- **开启前必须有条目**：空清单上开启等于把所有调用打成 `403`，平台会拒绝这个动作并提示你先加条目——这是「先配置再武装」，不是限制；
- 关闭之后，来源校验那一层的 `403 OPEN_API_SOURCE_IP_REJECTED`（**应用白名单腿**）不会再出现；**平台边缘腿**（对端地址判定）不受本开关影响，恒定生效。

**迁移动作**：无需迁移，API 合同零改动（没有新增/删除任何商家 API 字段与错误码）。若你的接入文档或运维手册里写着「白名单关闭须联系平台审核」，可以删掉这句；如果我们此前给过你「出口 IP 必须固定」的运维约定，现在多了一个自助选项，但**仍然建议保持开启**：密钥一旦外泄，它是签名之外唯一还挡在前面的东西。

#### 变更（2026-09-28）：开通申请判据简化（信用与域名核验不再是判据）

产品负责人拍板「简化开通申请，已经有商户号的卖家基本都能通过」，一键申请的自动审核判据由 5 条降为 **3 条**（判据版本 `openapi-auto-review-v3`）：

| 判据 | 状态 |
| --- | --- |
| 商家状态（在营中） | 保留 |
| 协议与同意书签署 | 保留 |
| 经营范围申报 | 保留 |
| ~~信用与争议记录~~ | **已退役**——新卖家本就没有信用记录，原判据对每一位新卖家都恒为「数据缺失」转人工；商家被停用/冻结等处置态仍由「商家状态」拦下 |
| ~~申报域名归属验证~~ | **已退役**——域名由你自己填写，**平台不做核验**；核验保留为门户里的**可选自助**，建议完成（归属更明确），但不核验也能开通 |

- 三项判据齐备即**自动开通**，不再因为「没有信用记录」「域名没验证」转人工；
- **域名归属从来不是运行时访问控制**：平台不会因为域名未验证而拒绝你的支付或回调；
- 已有的历史申请记录不受影响（历史判据结果原样保留）；历史申请的判据名仍可能显示为已退役的英文标识（如 `SVIP_VALID`），那是**历史事实**的照实呈现。

**迁移动作**：无需迁移。若你的接入文档/代码里写着「必须先完成域名归属验证才能开通」「没有信用记录会被转人工」，请一并删除该前置描述。

#### 变更（2026-09-27）：不再要求 SVIP 资格

开放平台**整条线**不再以会员等级（SVIP）为判据（产品负责人决定）：

- 应用一键申请的自动审核**不再因非 SVIP 转人工**（判据版本 `openapi-auto-review-v2`）；
- 商家 API 的**新增下单与重拉起不再要求 SVIP**——原来的「SVIP 资格」`403` 拒绝码**已从错误码总表移除**（若你的代码里有它的分支，可以删掉；保留也不会再被触发）；
- 已有的历史申请记录不受影响（历史判据结果原样保留）；商家准入仍要求**商家状态 ACTIVE** 且未被风控冻结。

**迁移动作**：无需迁移。若你的接入文档/代码里写着"需要 SVIP"，请一并删除该前置描述。

#### 文档修订（2026-09-27）

本轮为**对齐线上实际行为**的资料修订（无接口行为变更，接口侧唯一一处见下），要点：

- **关单 / 重拉起**：明确这两个端点**无请求体字段，但仍必须带 `Content-Type: application/json`**（接口侧同步修正为「空请求体按无请求体处理」——修复前不带请求体会被 `400` 拒，属缺陷修复，对已按文档接入的商家只会变宽松）。
- **请求头**：补齐六头的长度与字符集约束（`nonce` 16–64 位、`requestId` 8–128 位等）；越界与缺失共用同一句 `400`。
- **响应验签**：补齐 `CONTENT_TYPE` 归一化规则（小写、去 `;` 参数），并写明**哪些响应不带** `X-XD-Response-*`（鉴权链之前的拒绝）——按旧文做强制验签会每个响应都失败。
- **`X-XD-Request-Id` 例外**由两类更正为三类（增加请求体门卫拒绝）。
- **`notifyUrl`**：补齐四项真实前置（绝对 HTTPS、host 必须属于已验证域名、短信二次验证、审核通过才生效），并写明**未配置/未通过 = 不产生事件、事后不可补发**。
- **乱序判据**：`stateVersion` 当前恒为 `0`，改为按状态机判新旧。
- **回跳语义**：`returnUrl` 不是自动跳转，需买家点「返回商家」，且仅同一页面会话提供。
- **通道口径**：通道放行由平台整体控制、无自助查询面（原「去门户确认你的应用放行情况」有误）。
- **限额口径**：限额不在门户展示，调整走反馈渠道（原指引入口不存在）。
- **域名验证**：绝大多数失败是**终态**，需重新签发（原「核对后重新验证」会撞 `409`）；补单次申报上限 10 个。
- **指纹自检**：明确 PEM 的规范化规则（统一换行、去首尾空白后再取 SHA-256）。
- **示例与 demo**：示例补 `replayed`/`thresholdFen`、重试条目补「nonce 必须换新」、修正 PHP 覆盖声明与自检命令的工作目录；demo 修正 PC 微信单文案、去掉真实收银页没有的复制入口，并如实标注「通道闸门与四道前置门未模拟」。
- **接入地址（Base URL）下发面**：此前资料只说「开通时提供」、又不许印 host，卖家无处可取；现在**登录门户「应用凭证」页**即可看到并复制「接入地址」，文档同步改写（见 [接入指南 §1](./02-integration-guide.md)）。

#### 文档修订（2026-09-28 · 深度对齐复核批）

本轮对 12 篇文档 + Skill + 示例 + demo 与服务端实现做了**逐条深度复核**（无接口行为变更，只改表述与示例），修的是上一批的漏网与自相矛盾：

- **回跳口径统一**：接入指南与 webhook 篇里「支付完成后自动 `303` 跳回 `returnUrl`」的说法改正为「**买家点「返回商家」才回跳**，且仅同一页面会话、首次观察到支付成功时提供」——与收银页篇、与实现一致（按旧文设计落地页的商家会发现多数流程并不回跳）。
- **`CLOSED` / `FAILED` 不是终点**：补上「支付机构随后确认到账时订单会被**提升为 `SUCCEEDED`** 并推送 `PAYMENT_SUCCEEDED`」这条真实存在的迁移——把这两个状态建成吸收态会**丢掉已到账的事件**。接入指南的状态图与 webhook 篇同批补齐。
- **`stateVersion` 乱序指引清理（第二次）**：webhook 篇的落账骨架与 Skill 的上线清单里仍在教「用 `stateVersion` 判新旧」，同批删除，一律改为**按订单/退款状态机判**；demo 的 mock 平台同步改为恒 `0`（此前反而自增，会让按文档实现错语义的代码在自测里全绿）。
- **`GET` 不带 `Content-Type` 时签名串该行为空行**（新增说明）：`GET` 可以不带这个头，但不带时参与签名的是**空行**而不是 `application/json`——写错只拿到中性 `401`，此前资料里推不出这一支。签名规范篇与 API 参考同批补。
- **请求字段约束成表**（API 参考新增 §2.7）：`outTradeNo`/`outRefundNo` 6–64 位且**不能含点号**、`amountFen` `1`–`2000000`、`currency` 固定 `CNY`、`subject`/`description`/`attach`/`returnUrl`/`reason` 的长度上限与 https 要求——此前这些硬约束只存在于合同文件，卖家只能靠 `400` 反推。
- **业务摘要成员公开**：明确同号重试「同内容」的判定成员（含 `returnUrl`）——**改 `returnUrl` 再重试是 `409` 冲突而不是被忽略**；`payerClientIp` 不参与，可自由变化。
- **`400` 与 `422` 的分界**：单笔金额超出平台**合同硬上限**返回的是 `400 OPEN_API_BODY_INVALID`；`422 OPEN_API_LIMIT_EXCEEDED` 只用于平台限额。费率篇补出**日累计口径**（当日支付成功金额之和、**退款不释放额度**、北京时间自然日）与**待支付订单数 / 未关闭尝试数**两类此前完全没写的触发面，并说明实际生效的限额层级只有**两级**（结构性存在的「应用档位」当前没有写入面）。
- **事件体两处语义**：`status` 是**事件主体自身**的状态（退款事件里是退款状态，不是订单状态）；事件 nonce 是**事件级**的（重投复用同一 nonce，判重一律用 `eventId`）。「上限 8 次」改写为「**共投递 8 次**（首次即时 + 7 次退避）」，并如实写明**终止态之后平台不会自动感知**（需商家自查单/对账后申请人工补推）。
- **`403` 的两条腿**：区分**平台边缘腿**（带 `details.reason` 七种取值，加白名单无效）与**应用白名单腿**（三字段信封）；删去原先「`details` 含 `appId`」的承诺（该值不会出现在响应里）。安全红线 §8 的简写码名补注「信封里一律是全名」。
- **兜底与边界**：补「收到总表之外的 `code` 按 `503` 语义处置并反馈」、`413`/`500` 的存在说明、以及「路径/方法写错时拿到的不是本文档描述的信封」；`GET` 两个查询端点的失败码补 `409`（重放防护）；创建订单失败码删去不可达的 `404`；`X-XD-Sign` 补 `64–1024 位可见 ASCII`；拒绝次序按实际装配更正（**请求体门卫 → 来源 IP → 六头形态**）。
- **响应验签如实登记**：`XD-Response-v1` 目前**没有参考实现**（`examples/` 覆盖请求签名与事件验签），上线清单 A6 补注需自行按规范串实现；demo 的 mock 平台也**不回**四头。
- **demo 与生产对齐**：关闭/失败事件的 `eventAmountFen` 改为 `0`、`reason` 带上真实关闭原因、退款事件补 `outRefundNo`、`stateVersion` 恒 `0`；README 明示**本 demo 的请求体不是生产请求体形状**（生产以快速开始 §2 六个必填字段为准），并注明 `demo/` **不在门户两个下载包内**。
- **结算视图口径**：明确逐笔清单**只展示最近若干笔**，更早订单以自有记录 + 每单 `feeProjection` 对账。

## 4. 已取消/不支持的形态（历史公告残留，防误用）

平台**不提供**下列形态，任何历史资料、截图或口口相传里的这些说法都不成立：

- 微信「原生扫码」直出付款码（见上：不存在）。
